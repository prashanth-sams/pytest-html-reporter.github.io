Why this page exists

“What does this do that pytest-html doesn’t?” is the second question anyone evaluating a reporter asks, and until now the answer lived nowhere. This page is the answer, with two rules attached.

The first rule: every claim made here about this plugin comes from its own source, and the numbers are measured rather than rounded up. The second rule: claims about the other tools are kept to what this project can actually stand behind. Where that runs out, the table says check its docs instead of asserting a gap. A comparison page that scores every row in its own favour is not a comparison, and it does not get believed.

Careful Reporting tools move. Treat the columns for the other projects as a starting point and confirm the current behaviour in their own documentation before you decide on it.

The distinguishing bet here is one sentence: a single self-contained file that carries its own history. Everything else follows from that. The libraries are vendored and inlined so the file opens with no network. Each build’s output.json is archived so the next build can read it. The Analytics tab exists because that archive is already on disk. The 1.5 MB floor and the retention flags exist because of the first two. If a single file that opens anywhere is not something you need, one of the alternatives below is a lighter answer, and this page will tell you which.

pytest-html

The obvious comparison and the closest one. Both are pytest plugins that turn a run into an HTML report, and for a long time this project treated it as the benchmark: the entry in ROADMAP.md that added captured stdout, stderr and logging per test justified itself with the line “this is the biggest single gap versus pytest-html”. That gap is closed now, but the framing is worth repeating, because the remaining differences are narrower than a feature list makes them look.

Where this plugin goes further. History is the real one: pytest-html reports one run, and this one keeps an archive of previous builds and reads it, which is where Trends, Archives, Analytics, flaky-test detection, pass-rate drift and the delta against the previous build all come from. Then screenshots without wiring, an HTTP call log that records a whole request and response with credentials blanked out and offers the curl that repeats it, steps, and a Coverage tab read from whatever measured it.

Where pytest-html is the better answer. It is small, mature, and deeply extensible through hooks of its own. That last point is the honest weakness here: this plugin has no documented hook for adding a column, changing the layout or rendering a cell. Its customisation surface is the flags on the CLI reference, the attach and step helpers, --environment and --build-info for the Environment panel, and --report-link for extra side-nav entries. If you need to shape the report itself, that surface will run out.

Note If you only ever open the latest run, the history machinery is page weight you are paying for and not using. That is a real cost, not a rhetorical concession: a report starts at about 1.5 MB and grows by roughly 5 KB per retained build — more for a large suite, since the cost is per test per build. This project’s own suite runs about 7 KB a build.

allure-pytest

Allure is the richest reporting ecosystem in this space, with steps, attachments, severities, history and a polished UI, and first-class support across many languages rather than only Python. On features, it wins.

The difference that decides it is structural, and it is about the pipeline rather than the feature list. allure-pytest writes result files, and a separate allure command line tool, which needs a JVM, turns them into a report. That is two moving parts and a Java dependency in your build image, in exchange for a considerably deeper product.

This plugin writes the finished HTML at the end of the pytest run. There is no second step and no runtime beyond Python, and the result is one file you can attach to an email.

Pick Allure if your organisation already runs an Allure server, if you report from more than one language and want them in one place, or if you want the depth its model gives you. Pick this if the thing standing between you and a report is that nobody wants to install a JVM on the build agent — that is the situation this exists for.

JUnit XML, read by your CI’s own viewer

Every CI system reads JUnit XML, and it costs nothing: pytest writes it with --junitxml and there is nothing to install. It is also all it does. Pass/fail per test, no logs, no screenshots, no history, no HTML.

The important thing here is that this is not an either/or. This plugin will write the XML for you, from the same run and from the same records the HTML is built from.

shell One run, one set of records, two documents 
$ pytest tests/ --html-report=./report --report-junit=./report/results.xml

From a sharded matrix, the standalone merge command writes both from the merged bundles:

shell After the shards’ artifacts have been downloaded 
$ pytest-html-reporter merge artifacts/ \
    --html-report=./report \
    --junit-xml=./report/results.xml

Generating both from the same records means the XML and the HTML can never disagree about what happened. That is not true if you pass --junitxml and --html-report together and let two plugins count the run independently. The XML is written before the “did anything run?” guard, too, so a run that collected nothing still leaves a document saying so — a missing file reads to a CI system as a job that never ran. See the CLI reference for the shaping flags, and CI, xdist and scale for the sharded case.

Pick XML on its own when the pass/fail list in your CI’s own UI is all anyone actually opens, and you would rather not carry a multi-megabyte artifact per build.

pytest-json-report and pytest-reportlog

A different category rather than a competitor. They produce machine-readable output for you to build on, and no UI. If you are feeding a dashboard of your own, they are the right shape and this plugin is over-specified for the job.

Worth knowing before you decide: output.json is a documented, stable build record written beside every report, and it is what the Archives, Trends, Analytics and the VS Code extension all read. You can read it the same way, so one run can give you both the page and the data. The Python API page and Compatibility and files describe what is in it.

Pick pytest-html-reporter when…

  • You want one file you can send to someoneIt opens from an email attachment, a CI artifact server, a locked-down laptop or an archive years later, because every library and icon is inside it.
  • You want the run in context, without standing up a serviceTrends, the delta against the previous build, flaky tests and pass-rate drift all come out of a folder of JSON files next to the report.
  • Your suite drives a browserA failing Selenium or Playwright test is photographed with no hook, fixture or import, because the reporter finds the browser in the test’s own fixtures.
  • You write pytest-bdd scenariosGiven, When and Then arrive as timed steps with no changes to the feature files or the step definitions.
  • You already publish JUnit XMLAnd you would rather it came from the same records as the report than from a second plugin counting the same run.
  • Nobody wants another runtime on the build agentThe hard dependencies are pytest and Pillow; the merge command is argparse and the standard library, so CI can always run it.

Pick something else when…

  • You only ever read the latest runHistory is the reason for the page weight. If nobody opens Trends or Analytics, you are carrying the archive and the vendored libraries for nothing, and a lighter reporter is the better trade.
  • You need to shape the report itselfThere is no documented hook for adding a column, changing the layout or rendering a cell. If report customisation through hooks is the requirement, pytest-html is built for it and this is not.
  • A 1.5 MB artifact per build is too muchThat is the floor before any content, and this project’s own report with 296 archived builds is 3.5 MB. If your CI already renders pass/fail well enough, --junitxml costs kilobytes and nothing to install.
  • You already run Allure, or report from more than PythonA reporting stack your organisation has already standardised on beats a second one that only covers the Python suites.
  • You are building your own dashboardThe JSON reporters are the right shape for that. Read output.json if you want this plugin’s record too, but do not adopt the whole page for data you are going to re-render anyway.
  • You are pinned to an old interpreterThe tested band is Python 3.9 to 3.13 across Linux, macOS and Windows, with 3.8 as the practical floor. Older than that means pinning an old release and testing it yourself — see Compatibility and files.

Migrating from pytest-html

Running both at once

You do not have to choose on day one. These are independent pytest plugins: this one registers --html-report, --title, --environment, --build-info, the three --archive-* flags and the --report-* family, writes only its own files, and neither reads nor disables another reporter’s output. Install both, pass both flags, and one run produces both reports.

The one thing worth deciding early is the XML. If you keep another plugin’s report and also pass pytest’s --junitxml, two independent counts of the same run end up in two documents. Using --report-junit instead means the XML is built from the same records as the HTML.

What lands on disk

This is the surprise that catches most people, so it is worth doing before the first commit. With no --html-report, the report is written as pytest_html_report.html into the current working directory, which is usually your repository root, together with an output.json and — from the second run onwards — an archive/ folder. Nothing is cleaned up and nothing warns you.

output A finished report folder, once you have given it one 
report/
  pytest_html_report.html   the report
  output.json               this build, machine-readable
  archive/output_<ts>.json  every retained earlier build
  pytest_screenshots/*.png  the images

So give it a folder of its own and add that folder to .gitignore. Compatibility and files has the block to paste and the two path rules that surprise people.

The flags do not map one to one

There is no translation table, because the option sets do not line up: this plugin’s surface is a report path, a title, environment and build metadata, three retention flags, and the --report-* family that decides how much of each thing the page keeps. Every flag has a matching pytest.ini key except --title. Read the CLI reference once and set the ini keys rather than porting a command line across.

The first run has no history

Everything that makes this different from a one-run reporter reads the archive, and the archive starts empty. The first run produces a report with a Dashboard and a Test Metrics table and not much else; Trends needs a second build to have a line, and flaky-test detection needs enough builds for a status to have flipped. Do not judge it on run one.

What you can turn off

If the page is heavier than you want, the levers are retention and capture rather than a different reporter. --archive-count, --archive-days and --archive-since intersect to decide which builds survive, and pruning the folder shrinks the page for free at roughly 5 KB per build. --report-logs, --report-attachments, --report-steps and --report-screenshots each narrow or switch off what is kept per test. The Configuration page has all of them, and Security and privacy covers the same flags from the other direction — what ends up in a report you are about to publish.
