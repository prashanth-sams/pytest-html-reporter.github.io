Quickstart

Three minutes to your first report

Nothing to register, nothing to import. Add the package, run pytest, and the report is waiting in report/ — and on a local run it opens by itself.

  1. Install

    One package. It registers itself with pytest through an entry point.

  2. Run your suite

    No flags needed. Add --html-report only if you want a different path, filename or title.

  3. Open the page

    A single HTML file you can email, attach to a ticket, or publish to Pages as-is.

Full getting-started guide
shell 
$ pip3 install pytest-html-reporter
$ pytest tests/

# -> ./pytest_html_report.html
shell 
$ pytest tests/ --html-report=./report/report.html --title='PYTEST REPORT'

# strftime placeholders give each run a folder of its own
$ pytest tests/ --html-report=./reports/%Y%m%d/report_%H%M.html
ini 
[pytest]
addopts = --html-report=./report --title='Nightly'
report_screenshots = failed
It opens itself On a local run the finished report is opened in your browser. On a build agent it stays quiet — CI is detected, not guessed at.

What is in the page

Everything a failing build makes you ask

A pass/fail count tells you how much went wrong. Here is the whole of what the report tells you instead — thirty-nine of them, in one HTML file, with nothing to switch on.

The page itself

5
  • One static HTML fileNo server, no asset folder, no build step. Mail it, publish it, open it off a stick.
  • It opens itselfAfter a local run the finished report is in your browser. CI is detected, not guessed at.
  • Light and dark themesFollows the machine, remembers the choice, and prints legibly either way.
  • Titled and badged--title names the report, --environment puts a badge beside it.
  • Links of your own in the side navPoint at annotated coverage, a CI job or a wiki page. Repeat the flag as often as you like.

Reading a run

6
  • OverviewThe donut, the PASS / FAIL / SKIP / XPASS / XFAIL / ERROR counts, and the time it took.
  • TrendsPassed, failed and skipped plotted across this run and the five builds before it.
  • HighlightsThe suite that failed most, and which way the failure count has moved.
  • Test suite detailsEvery suite with its own counts, so a failure concentrated in one file shows up early.
  • The Test Metrics tableSearch, sort, ten columns, and exports to copy, CSV, Excel, print and column visibility.
  • Environment & build detailsWhat the run was, what it was told about the build, and what it kept of the output.

Coverage

3
  • A Coverage tab, if it was measuredThe ring, the counts, a row per file with its missing lines, least covered first.
  • The trend, and the project's own bar+0.8 since the last build, coloured at --cov-fail-under rather than at a guess.
  • Coverage measured somewhere elseCobertura XML, coverage.json or a data file, recognised by content, not by name.

Steps, Gherkin & markers

4
  • Named, timed, nested stepsSuite down to test down to what it did, with the failing step carrying the message.
  • A tree even without stepsSet up, body and tear down are timed for every test, whether or not you named anything.
  • Gherkin scenariosA pytest-bdd scenario arrives already named, badged, and filled in from the row that ran.
  • Markers, and where they came fromIncluding the module-level and class-level ones nobody remembers applying.

Reading a failure

5
  • Why this run failedFailures grouped by exception, biggest first — 12 failures, 9 are TimeoutException.
  • The failure delta▲ +3 failures since last build, red when it is going the wrong way.
  • Copy the error, or the rerun commandThe full message, or pytest path::test built from the node id and quoted for a shell.
  • Deep links to a single rowAn address per test that survives a re-sort, a search and a page of the table.
  • Status filter chipsOne click for "show me only the failures", driven off the Dashboard counts.

How a test behaves

5
  • Stability scoreOne number out of 100 for the suite, charged for flipping as well as for failing.
  • Flaky testsTests that have flipped, or needed a retry to pass — kept apart from the rest.
  • Always failingFailed every build they were in. A bug with an owner, not a race worth hunting.
  • Pass rate across buildsOn an axis that is not pinned to 0–100, so a two-point drop is visible.
  • Where the time goesThis run's tests bucketed by duration — what a slowest-tests list cannot tell you.

Evidence

5
  • Screenshots, taken for youA failing Selenium or Playwright test is photographed. No hook, no fixture, no import.
  • Attachments & API logsBoth bodies, both sets of headers, and the curl that repeats the call.
  • Credentials blanked outTokens, cookies and auth headers are redacted — a report is a build artifact.
  • Captured stdout, stderr & loggingKept per test and on by default, opened section by section with a copy button.
  • Truncation that says soA cut message fades rather than lying by omission in a file read a week later.

History

3
  • Every build kept in the pageRoughly 5KB each, and the source of Trends, the delta and the whole Analytics tab.
  • Retention by count, age or dateThe three limits intersect, and are usually better written down in the ini file.
  • Dated by the run, not the fileAn age limit still measures the right thing after CI copies the reports elsewhere.

Running it at scale

3
  • One report from an xdist runWorkers are merged into a single build, listed in collection order. Nothing to configure.
  • Reruns and retriesEvidence survives a green retry, and a retried test keeps its history straight.
  • Matrix runsA job per Python version or per browser, each writing where you tell it to.
