# pytest-html-reporter.github.io

The documentation site for [pytest-html-reporter][lib] and its two companion projects,
the [GitHub Action][action] and the [VS Code extension][vscode].

Static HTML. No framework, no bundler, no npm. GitHub Pages serves `index.html` and
everything under `docs/` exactly as it is committed.

## Layout

```
index.html               the landing page (hand-written, standalone)
404.html                 served by Pages for any unknown path
docs/*.html              the built documentation pages  ← committed, served
content/*.html           the source fragments for docs/ ← edit these
tools/build.py           wraps a fragment in the shared shell
tools/check.py           structure: links, ids, unescaped code
tools/facts.py           content: every name against the three source repos
tools/shots.py           regenerates SCREENSHOTS.md
assets/css/site.css      the design system
assets/js/site.js        theme, nav, copy buttons, highlighting, scrollspy, search
assets/search-index.json generated by build.py, read by the search dialog
assets/img/              logo, favicon
assets/img/shots/        screenshots the pages reference
assets/img/shots/captured/  staged captures of a real report, not yet used
sitemap.xml, robots.txt  generated by build.py
```

## Checking it

```console
$ python3 tools/build.py       # regenerate docs/ from content/
$ python3 tools/check.py       # structure: broken links, duplicate ids, unescaped code
$ python3 tools/facts.py       # content: every flag, input and setting against the real repos
$ python3 tools/shots.py       # rewrite SCREENSHOTS.md from the placeholders in the pages
```

`tools/facts.py` is the one worth running before a release. It reads the ground truth out of the
three source repos — the options `pytest_addoption` registers, the keys `addini` declares, the
inputs and outputs in `action.yml`, the commands and settings in the extension's `package.json` —
and reports any name the docs use that no longer exists, plus the handful of facts that are easy
to get wrong and expensive to get wrong. It expects the repos beside this one; pass `--repos DIR`
if they live somewhere else.

`tools/build.py --check` exits non-zero when a built page is out of date with its fragment, which
is what a CI job would run.

## Editing a page

Edit the fragment in `content/`, then rebuild:

```console
$ python3 tools/build.py
```

No dependencies — the standard library is enough. `tools/build.py --check` exits non-zero if a
built page is out of date, which is what a CI job would run.

Code blocks carry a `data-lang` that drives the highlighter: `shell`, `python`, `yaml`, `ini`,
`json`, `toml`, `gherkin`, or `output` for program output that should not be coloured at all.

Each fragment starts with a one-line JSON front-matter comment:

```html
<!--META {"title": "Getting started", "eyebrow": "Introduction", "description": "…", "lede": "…"} -->
```

Everything after it is the body. The builder supplies the `<head>`, the top nav, the sidebar, the
breadcrumbs, the page heading, the on-this-page table of contents, prev/next and the footer — so
a fragment never contains an `<h1>` and never repeats the chrome.

Adding a page means creating `content/<slug>.html` and adding the slug to `SIDEBAR` in
`tools/build.py`. The sidebar order is also the prev/next order.

## Search

Client-side, no service and no account. `tools/build.py` writes
`assets/search-index.json` alongside the pages: one record per `h2`/`h3` section,
carrying the heading, the page it belongs to, the opening of the section and the
code tokens it contains — the flags, ini keys and file names a reader types
verbatim. A result therefore lands on the heading it matched rather than at the
top of a two-thousand-word page.

The index is around 130 KB gzipped, so `assets/js/site.js` fetches it on the
first open rather than on every page load, and never at all for a reader who
does not search. Ranking is heading match first, then the code tokens, then the
body, weighted by how much of the heading the term covers and how often the
section says it; sections that score the same appear in sidebar order. Multiple
words are an AND, and a query that matches nothing is retried against word
stems, so "installation" still finds "Install it".

`⌘K` or `Ctrl+K` opens it from anywhere, `/` opens it when focus is not in a
field, arrows and Enter work the list, Escape closes. Nothing to rebuild by
hand — the index is regenerated by every `tools/build.py` run, and needs to be
committed with the pages it describes.

## Themes

Light and dark, both first-class. The palette lives in `:root` and `:root[data-theme="dark"]` in
`assets/css/site.css`, and is keyed to the same blue, yellow and grey as the project logo. A
small inline script in each page's `<head>` sets the theme before first paint, so a dark reader
never sees a white flash. The reader's choice is kept in `localStorage`; until they make one, the
site follows the operating system.

## Screenshots

Pages carry dashed placeholder slots where a picture belongs, each naming the exact file it
wants:

```html
<figure class="imgslot" data-shot="report-overview.png">…</figure>
```

Drop the image at `assets/img/shots/<name>` and replace the `<figure class="imgslot">` with:

```html
<figure class="shot">
  <img src="../assets/img/shots/report-overview.png" alt="…" loading="lazy">
  <figcaption>…</figcaption>
</figure>
```

`grep -rho 'data-shot="[^"]*"' content/ | sort -u` lists everything still outstanding.
